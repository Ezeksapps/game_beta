PLAN FOR MOVEMENT IMPLEMENTATION
--------

Movement is dealt with one tile at a time (Z axis only considered when detecting collision, else ignored and world treated as 2D)
The translation is turned into a transform matrix which is multiplied by the model matrix to get the new model matrix

However, the translation is not instant. All movement also plays an animation (ANIM_EVENT_WALK) via the sprite sheet system
One complete instance of the animation needs to play to move one tile in any direction. The translation of the sprite billboard
needs to move smoothly as that animation plays, moving in small incremental steps every frame the animation plays until arriving at the
final position when the animation ends. If another invokation of Entity::move() occurs, then this repeats. Otherwise, the entity stops moving
and goes to the idle state (ANIM_EVENT_IDLE)

So, to do this, find the total number of frames the animation plays for (loop through m_pActiveSprite->frameDurations and sum all values)
This will be the number of smaller translations that will be applied to this entity (one per frame)
The transform matrix applied every step will always be the same, since these steps are all equally sized.
To find the translation vector, do:
vec3 translVec = vec3(dx / animFrames, dy / animFrames, 0.0f /* Z-axis ignored */);

Then form the transform matrix from this.
The Renderer needs to now be signalled to start the translations for the required number of frames, but class Entity cannot access
Renderer. (Since the doesn't make sense) So, like for sprite sheet animation switching, add a callback to Entity that the renderer can
attach a function to. The callback runs whenever Entity calls it an invokes the function inside the renderer allowing it to process the transformation

UPDATE:
Model matrix is calculated on every update() call, transform matrix can auto form, tranlVec is all that's needed for callback

Movement lag
-=-=-=-=-=-=-=-

The instance data upload is technically computationally expensive but there is currently only one entity which means instance data only has
one index at all times. considering that this isn't a low-end PC and the draw calls are all relatively simple, there is no reason to conclude that
the instance data upload is the issue. The geometry shader must also be running at sufficient frequency since the idle animation renders fine
issues only exist when the sprite is moving, the enity does move to its proper position and debug shows the geometry must be moving but the sprite
meant to be visible isn't. it cannot be an issue with the sprite sheet system since animations without a moving entity play fine, the switch back
to the idle animation also executes fine.

I also did a test where I did not reset to the idle animation following the translation. The walking animation plays just fine after movement
completes and continues in a loop, it is specifically during movement that somehow the draw does not work properly, despite geometry clearly
moving as expected

Frame rate cannot be the issue since the animation speed is tied to the frame rate (the rate at which update() is called) and, as stated
previously, animations play fine with expected behaviour.

Shaders in OpenGL/Vulkan will run every frame, specifically:
[https://stackoverflow.com/questions/35243518/frequency-of-shader-invocations-in-rendering-commands]
VS runs once per vertex assuming non-indexed drawing (may be less if using indexed draw calls)
GS runs once for every input geometry (In this case for every point vertex, which is the centre positions of all billboard quads)
FS runs at least once for every pixel-sized area covered by the primitive being rasterised

A test to check if the geometry shader is the issue is to set the fragment shader to ignore texture and just draw opaque green to the quad,
if this moves smoothly, GS is fine, otherwise, GS is probably the issue

Test showed that the green never stopped rendering, meaning the quad was at no point destroyed, but did still show laggy movement rather
than the smooth movement that is expected to result from the gradual translation system, though some intermediate steps can be seen
The issue is definitely to do with the way these gradual translations are being done, which is computationally expensive

https://stackoverflow.com/questions/2807053/how-to-make-smooth-movements-in-opengl
This confirms it, instead use interpolation while storing the final position immediately then do the translation on a timer

The interpolation here refers to calculating intermediate positions, which is done through linear interpolation (lerp)
GLM provides a function for this glm::lerp() though this might not be useful if I'm doing the interpolation shader-side
a generic lerp function is:

(from https://bsmarted.com/en/topics/opengl/implementing-animation-basics)

float lerp(float start, float end, float t) {
    return start + t * (end - start);
}

where t is the progression between the keyframes (a keyframe is a specific state defining either the start or end point of a smooth animation)

lerp is not to be confused with spherical linear interpolation (slerp), which is good for perfoming smooth rotations

However, this is not technically any less computationally expensive than the other method I was using

A further experiment I did was to set animFrames to a hgher value. The animation assigned to ANIM_EVENT_WALK was 26 frames, but I overrode this and set
animFrames to 55 to see what would happen. When this is done, the walk animation is visibly played (the fps drop remains) for about 1/2 cycles,
which doesnt make sense since 1/2 cycles of the walk anim would be 39 frames

Scaling issues
-=-=-=-=-=-=-=-=-

Now that most of the essential components of the renderer are finished and stable, there is another problem that needs to be dealt with.
All overworld Pokemon sprites used in this projects are taken from the PMD sprite repo.
The format of these sprites is essentially the baseline for the sprite format in this game, but one part of this is that the sprites can have
different frame dimensions. For example, in the test sprite sheets I was using, the walk sprite is 48 x 40 and the idle sprite 32 x 24

up until this point, I had been upscaling all the sprites so the frames were 192 x 192 (so they fit perfectly into the tex array), but
that won't work anymore. Even if I upscale both of those the original frame dimensions are still different. These are being stuck on a quad that
is always the same size, no matter what. This means the smaller idle sprite looks larger than the walk sprite

This is not desireable, the billboard geometry will need to be scaled so that the percieved size of the sprites is consistent

Also, a small modification will need to be made to the tex array. Now 192 needs to be switched to a constant, so if i ever need it changed, I can
do that without editing the multiple places it appears. Two constants will be used, one for width and one for height, where the height has a higher allowance
The reason for this is simply because the PMD sprites are usually taller than they are wide
The two new constants will be m_maxSpriteFrameHeight and m_maxSpriteFrameWidth

Of course, this is now a max -- not all sprites will be those dimensions. Dimensions will now become properties of the Sprite struct as well,
stored as 'frameWidth' and 'frameHeight'. (entity will set these in the constructor when it loads the sprite sheet JSON)
The math for the copying and loading into the tex arrays will need to be adjusted to use the actual dimensions instead of assuming
all sprites carry the max dimensions. The tex arrays are still sized to allow sprites with frame sizes up to the max capacity,
just that if the sprites a lower than max capacity, that extra space will go unused

[https://www.reddit.com/r/opengl/comments/hkno6c/can_i_create_an_2d_texture_array_with_different/]
[https://gamedev.stackexchange.com/questions/121215/can-i-create-an-2d-texture-array-with-different-sizes-for-each-textures]

It also needs to use UVs that map only to the section of the slice actually being used (since frames will almost always be smaller than slice dimensions)
The OpenGL code from the stackexchange post can be adapted for that. The minimum UV coordinates are always 0, 0. The maximum UVs can be calculated
C++-side and uploaded as instance data to the geometry shader

Multiple entities
-=-=-=-=-=-=-=-=-=-

Theoretically, the engine was in a state where multiple entities could be properly rendered at once. After all, the back end C++
code was complete and fully tested, so the values being set in m_instanceData should be correct and thus the data the shader recieves should be correct.

Testing multiple entities following the creation of the basic Scene JSON format (so entities can now be added/removed without hard-coding and needing to recompile every time)
showed that this was not the case. Initially, I only saw the first entity. When I tried to debug the shader I got other weird results like another quad forming,
but in the wrong location and showing the same sprite as the first entity. Since it appeared the geometry itself was never being formed, i tested the geometry shader's logic
by implementing it C++ side just before the instance data upload and printing (std::cout) the results. These were completly fine

A test in the geometry shader where i overrode the input matrix completely and set it to depend on the instance ID showed that all the shader pipeline was indeed
running for 3 instances (Which was expected behaviour, I was testing rendering for three entities), three quads were drawn side-by-side.

pos = vec3(float(instID) * 2.0, 0.0, 0.0);

If setting the centre position of the billboard in the geometry shader fixed the issue, then that meant the inputs were incorrect for everything that wasn't the first entity
This showed that the issue was input layout.

To test, I tried setting the input layout in the PSO creation with manual relative offsets and strides. I did make a small syntax error when I first did it
(this being misunderstanding how to use the stride parameter), but that syntax error ended up revealing the problem through the debug logs:

Diligent Engine: ERROR: Inconsistent strides are specified for buffer slot 0. Input element at index 4 explicitly specifies stride 4, while current value is 16. Specify consistent strides or use LAYOUT_ELEMENT_AUTO_STRIDE to allow the engine compute strides automatically.
Diligent Engine: ERROR: Stride 4 explicitly specified for slot 0 is smaller than the minimum stride 76 required to accommodate all input elements.

Diligent was previously simply allowed to automatically set stride, which these logs show was being treated as 16. The size in bytes of one instance of InstanceData is actually 76
This explains why the other two entities did not display or even have their quads form, the shaders were being given the data with incorrect stride information

[Note to self, a similar thing already happened when first making the Scene/map renderer pipeline. Remember, always check the input layout (so you don't spend
2 days thinking you've gone crazy)]
