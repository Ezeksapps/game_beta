PLAN FOR MOVEMENT IMPLEMENTATION
--------

Movement is dealt with one tile at a time (Z axis only considered when detecting collision, else ignored and world treated as 2D)
The translation is turned into a transform matrix which is multiplied by the model matrix to get the new model matrix

However, the translation is not instant. All movement also plays an animation (ANIM_EVENT_WALK) via the sprite sheet system
One complete instance of the animation needs to play to move one tile in any direction. The translation of the sprite billboard
needs to move smoothly as that animation plays, moving in small incremental steps every frame the animation plays until arriving at the
final position when the animation ends. If another invokation of Entity::move() occurs, then this repeats. Otherwise, the entity stops moving
and goes to the idle state (ANIM_EVENT_IDLE)

So, to do this, find the total number of frames the animation plays for (loop through m_pActiveSprite->frameDurations and sum all values)
This will be the number of smaller translations that will be applied to this entity (one per frame)
The transform matrix applied every step will always be the same, since these steps are all equally sized.
To find the translation vector, do:
vec3 translVec = vec3(dx / animFrames, dy / animFrames, 0.0f /* Z-axis ignored */);

Then form the transform matrix from this.
The Renderer needs to now be signalled to start the translations for the required number of frames, but class Entity cannot access
Renderer. (Since the doesn't make sense) So, like for sprite sheet animation switching, add a callback to Entity that the renderer can
attach a function to. The callback runs whenever Entity calls it an invokes the function inside the renderer allowing it to process the transformation

UPDATE:
Model matrix is calculated on every update() call, transform matrix can auto form, tranlVec is all that's needed for callback

Movement lag
-=-=-=-=-=-=-=-

The instance data upload is technically computationally expensive but there is currently only one entity which means instance data only has
one index at all times. considering that this isn't a low-end PC and the draw calls are all relatively simple, there is no reason to conclude that
the instance data upload is the issue. The geometry shader must also be running at sufficient frequency since the idle animation renders fine
issues only exist when the sprite is moving, the enity does move to its proper position and debug shows the geometry must be moving but the sprite
meant to be visible isn't. it cannot be an issue with the sprite sheet system since animations without a moving entity play fine, the switch back
to the idle animation also executes fine.

I also did a test where I did not reset to the idle animation following the translation. The walking animation plays just fine after movement
completes and continues in a loop, it is specifically during movement that somehow the draw does not work properly, despite geometry clearly
moving as expected

Frame rate cannot be the issue since the animation speed is tied to the frame rate (the rate at which update() is called) and, as stated
previously, animations play fine with expected behaviour.

Shaders in OpenGL/Vulkan will run every frame, specifically:
[https://stackoverflow.com/questions/35243518/frequency-of-shader-invocations-in-rendering-commands]
VS runs once per vertex assuming non-indexed drawing (may be less if using indexed draw calls)
GS runs once for every input geometry (In this case for every point vertex, which is the centre positions of all billboard quads)
FS runs at least once for every pixel-sized area covered by the primitive being rasterised

A test to check if the geometry shader is the issue is to set the fragment shader to ignore texture and just draw opaque green to the quad,
if this moves smoothly, GS is fine, otherwise, GS is probably the issue

Test showed that the green never stopped rendering, meaning the quad was at no point destroyed, but did still show laggy movement rather
than the smooth movement that is expected to result from the gradual translation system, though some intermediate steps can be seen
The issue is definitely to do with the way these gradual translations are being done, which is computationally expensive

https://stackoverflow.com/questions/2807053/how-to-make-smooth-movements-in-opengl
This confirms it, instead use interpolation while storing the final position immediately then do the translation on a timer

The interpolation here refers to calculating intermediate positions, which is done through linear interpolation (lerp)
GLM provides a function for this glm::lerp() though this might not be useful if I'm doing the interpolation shader-side
a generic lerp function is:

(from https://bsmarted.com/en/topics/opengl/implementing-animation-basics)

float lerp(float start, float end, float t) {
    return start + t * (end - start);
}

where t is the progression between the keyframes (a keyframe is a specific state defining either the start or end point of a smooth animation)

lerp is not to be confused with spherical linear interpolation (slerp), which is good for perfoming smooth rotations

However, this is not technically any less computationally expensive than the other method I was using

animFrames to 55 to see what would happen. When this is done, the walk animation is visibly played (the fps drop remains) for about 1/2 cycles,
which doesnt make sense since 1/2 cycles of the walk anim would be 39 frames

Scaling issues
-=-=-=-=-=-=-=-=-

Now that most of the essential components of the renderer are finished and stable, there is another problem that needs to be dealt with.
All overworld Pokemon sprites used in this projects are taken from the PMD sprite repo.
The format of these sprites is essentially the baseline for the sprite format in this game, but one part of this is that the sprites can have
different frame dimensions. For example, in the test sprite sheets I was using, the walk sprite is 48 x 40 and the idle sprite 32 x 24

up until this point, I had been upscaling all the sprites so the frames were 192 x 192 (so they fit perfectly into the tex array), but
that won't work anymore. Even if I upscale both of those the original frame dimensions are still different. These are being stuck on a quad that
is always the same size, no matter what. This means the smaller idle sprite looks larger than the walk sprite

This is not desireable, the billboard geometry will need to be scaled so that the percieved size of the sprites is consistent

Also, a small modification will need to be made to the tex array. Now 192 needs to be switched to a constant, so if i ever need it changed, I can
do that without editing the multiple places it appears. Two constants will be used, one for width and one for height, where the height has a higher allowance
The reason for this is simply because the PMD sprites are usually taller than they are wide
The two new constants will be m_maxSpriteFrameHeight and m_maxSpriteFrameWidth

Of course, this is now a max -- not all sprites will be those dimensions. Dimensions will now become properties of the Sprite struct as well,
stored as 'frameWidth' and 'frameHeight'. (entity will set these in the constructor when it loads the sprite sheet JSON)
The math for the copying and loading into the tex arrays will need to be adjusted to use the actual dimensions instead of assuming
all sprites carry the max dimensions. The tex arrays are still sized to allow sprites with frame sizes up to the max capacity,
just that if the sprites a lower than max capacity, that extra space will go unused

[https://www.reddit.com/r/opengl/comments/hkno6c/can_i_create_an_2d_texture_array_with_different/]
[https://gamedev.stackexchange.com/questions/121215/can-i-create-an-2d-texture-array-with-different-sizes-for-each-textures]

It also needs to use UVs that map only to the section of the slice actually being used (since frames will almost always be smaller than slice dimensions)
The OpenGL code from the stackexchange post can be adapted for that. The minimum UV coordinates are always 0, 0. The maximum UVs can be calculated
C++-side and uploaded as instance data to the geometry shader

Theoretically, the engine was in a state where multiple entities could be properly rendered at once. After all, the back end C++
code was complete and fully tested, so the values being set in m_instanceData should be correct and thus the data the shader recieves should be correct.

Testing multiple entities following the creation of the basic Scene JSON format (so entities can now be added/removed without hard-coding and needing to recompile every time)
showed that this was not the case. Initially, I only saw the first entity. When I tried to debug the shader I got other weird results like another quad forming,
but in the wrong location and showing the same sprite as the first entity. Since it appeared the geometry itself was never being formed, i tested the geometry shader's logic
by implementing it C++ side just before the instance data upload and printing (std::cout) the results. These were completly fine

A test in the geometry shader where i overrode the input matrix completely and set it to depend on the instance ID showed that all the shader pipeline was indeed
running for 3 instances (Which was expected behaviour, I was testing rendering for three entities), three quads were drawn side-by-side.

pos = vec3(float(instID) * 2.0, 0.0, 0.0);

If setting the centre position of the billboard in the geometry shader fixed the issue, then that meant the inputs were incorrect for everything that wasn't the first entity
This showed that the issue was input layout.

To test, I tried setting the input layout in the PSO creation with manual relative offsets and strides. I did make a small syntax error when I first did it
(this being misunderstanding how to use the stride parameter), but that syntax error ended up revealing the problem through the debug logs:

Diligent Engine: ERROR: Inconsistent strides are specified for buffer slot 0. Input element at index 4 explicitly specifies stride 4, while current value is 16. Specify consistent strides or use LAYOUT_ELEMENT_AUTO_STRIDE to allow the engine compute strides automatically.
Diligent Engine: ERROR: Stride 4 explicitly specified for slot 0 is smaller than the minimum stride 76 required to accommodate all input elements.

Diligent was previously simply allowed to automatically set stride, which these logs show was being treated as 16. The size in bytes of one instance of InstanceData is actually 76
This explains why the other two entities did not display or even have their quads form, the shaders were being given the data with incorrect stride information

Improving movement
-=-=-=-=-=-=-=-=-=-=-

Better movement behaviour would ditch the grid and have a press of a movement key to signify: keep smoothly moving by the translVec every frame until the key is released
currently, move() can only move by 1 unit in the coordinate space

To implement this version of movement, the single movement callback, which creates an EntityTransl object
that allows the renderer to automatically terminate the movement when the entity has moved 1 unit, needs
to be separated into three callbacks. One for starting movement, one for changing movement direction
and one for ending movement

EntityTransl is no longer needed, as the only fields that are now useful are the translVec and the index of the entity it is associated
with, the vector of EntityTransl objects now becomes an unordered map

The input handler for movement also needs to be re-written. Previously whenever GLFW detected a keypress,
it would be added to a command queue in the engine. The keycode is not sent directly. To allow me to later
include a setting to re-bind keys I declare an enumerated type 'GameCmd' listing all possible commands the game can handle
and through a JSON these GameCmds are all assigned a GLFW key. This JSON was loaded when launching the game to populate
the key map, which allowed the code to match the recieved GLFW enum keycode to the matching GameCmd and add it to the command queue.
The input handler function then attached itself as a callback for a function that dequeued the next command and performs the appropriate action

(This system being based on one I had developed prior to this project, except in C++ rather than C)

The issue with this system is that it can only handle commands mapped to one key. The planned diagonal movement is activated
by pressing two movement keys at once. This also doesn't support the new expected behaviour for movement, as when holding
any movement key, this system will enqueue a very large number of movement commands, meaning that instead of the expected behaviour
where releasing all movement keys immediately terminates movement, the entity will instead not stop until all of those enqueued movement
commands have been cleared. Also, the new expectation is that a single keypress of any moveent key merely turns
an entity to face that direction, which needs to be assigned to a different command to actual movement.

This new system needs to be able to:
- handle and map game commands requiring multiple simultaneous keypresses
- handle continuous keypresses and distinguish general game commands from movement commands

The JSON structure of the key config has also been revised.
Now every command is its own separate object

There are three distinct types of command enumerators. Those representing single actions (GameCmd), those which begin a continuous action (MovementCmd)
and those which terminate a continuous action (MovementCmd)

single-action game commands are activated by pressing their corresponding key(s) once and immediately releasing
continuous action game commands are activated by holding their corresponding key(s). In this situation, the engine
will dispatch the command beginning the continuous action once only. The corresponding GameCmd which ends this action
will be dispatched when the key(s) corresponding to the continuous action are released.

A GameCmd or MovmentCmd enumerator (excluding continuous action terminators) can be set to activate on the keypress of one or multiple keys,
the maximum being two keys for now. The keycodes which correspond to enumerators are in different two different maps,
one for single actions (GameCmd) and one for continuous actions (MovementCmd)

These keycodes are not the GLFW enumerators for keys, they are unsigned 32-bit integers (uint32_t) which are considered as being split
into two separate unsigned 16-bit integers (uint16_t), where each of these matches the value of the GLFW enumerator. This allows up to two
keycodes to be stored and mapped to a GameCmd. Using a vector of integer types as the key instead is not practical as the std::unordered_map
container has no default hash function for vector keys

The GLFW keypress callback function body now looks like this:

if (action != GLFW_RELEASE) g_pEngine->signalKeyPress(key);
else g_pEngine->signalKeyRelease(key);

issues:
1. if you dont intend to just change the direction you face, there is a very annoying delay before you
actually begin movement due to when GLFW decides to start detecting GLFW_REPEAT events
2. I cannot move north-west, or face that direction
3. sometimes, due to something which needs to be determined (which may cause 2 as a side-effect), you stop being
able to move either entirely or just in certain directions, ENTITY_FACE_XXX commands will still work
4. If in diagonal moveent you let go of one of the keys, your movement direction will update.
But if you are moving straight in any direction and then hold a key to move diagonally, the new ENTITY_FACE_XXX
commands registers, but the movement direction never updates

05/09/2026 better idea:

GLFW will only provide limited information about a key's state. There are three 'events' GLFW_PRESS, GLFW_RELEASE & GLFW_REPEAT
so the best way to handle which keys are currently pressed will be to insert every recieved key into a set of pressed keys. The key is
removed from the set if GLFW_RELEASE is recieved. GLFW_REPEAT will not be used directly, but it will re-send a key code if that key is being
held for longer than the OS's interval that determines when it considers a key to be held. Because all pressed keys are stored in a set, I can
immediately attempt an insertion of the keycode (a set will not accept duplicate elements)

after adding a recieved key to the set, check which commands need to be issued.


void Engine::signalKeyRelease(const int& keycode) {

    activeKeys.erase(keycode);

    if (movementCmds.contains(keycode)) {
        switch (activeMovement) {

            // if the active movement wasn't diagonal, then just stop movement
            case ENTITY_MOVE_SOUTH:
            case ENTITY_MOVE_EAST:
            case ENTITY_MOVE_NORTH:
            case ENTITY_MOVE_WEST:
                activeMovement = ENTITY_STOP_MOVEMENT;
                break;

            // don't stop movement immediately. If the active movement is diagonal, then the new movement command
            // needs to be set to whichever one the other active movement key maps to
            case ENTITY_MOVE_SOUTH_EAST:

                break;
            case ENTITY_MOVE_NORTH_EAST:
                activeMovement = ENTITY_MOVE_EAST;
                break;
            case ENTITY_MOVE_NORTH_WEST:
                break;
            case ENTITY_MOVE_SOUTH_WEST:
                break;
        }
    }
}

Intended behaviour in the diagonal cases is to check which of the two keys was released and revert to the single-key action
so for example in case ENTITY_MOVE_SOUTH_EAST, check if the key assigned to moving south or east was the one released. If it's
the one for moving south, move east. If it's the one for moving east, move south. This is a problem because I can't check which
commands are assigned to which keycodes. C++ maps map a key to a value. The value isn't hashed to form a proper key, so I can't use
std::unordered_map<uint32_t, MovementCmd> movementCmds; to get a 32-bit key code from a MovementCmd, because the movement command isn't
a key

The simplest solution is to make a reverse map which maps MovementCmds to their corresponding key codes, but that is technically duplicate
data. I want to avoid wasted space and unecessary duplication as much as possible.
The only data I specifically need to accomplish the desired functionality is the 32-bit keycode representing the key(s) which produced
the currently active movement command. So, a better solution would be to just store this code only alongside the active movement command
in a separate variable

Another issue was that the handling of the current movement command was still attached to a callback that ran every time gameUpdate() was called
This is wrong, move() and endMovement() should only be called once, not repeatedly every frame. This also doesn't properly update the visible movement
unless ENTITY_STOP_MOVEMENT was issued prior to changing direction, as the previous move() call is still active and was never terminated.
What should instead happen is that the callback is executed only when the value of activeMovement needs to be changed

pseudocode impl of new callback:

if (prevMovementCmd == ENTITY_STOP_MOVEMENT) {
   if (newMovementCmd == prevMovementCmd) return;
   else entity->move(movementCmd, ANIM_EVENT_WALK);
}
else if (newMovementCmd == ENTITY_STOP_MOVEMENT) entity->endMovement();
else entity->changeMovementDirection(movementCmd);



Collision Detection
-=-=-=-=-=-=-=-=-=-=-=-

Sprites themselves are very simple geometry-wise, as they are made up of only a single quad
The best way to do collision detection for them is therefore with an AABB algorithm (axis-aligned bounding box)
This is fine for collisions between entities, but I also need to consider collision between an entity an the surrounding 3D scene.

Entities should be able to travel around the scene freely as long as they do not overlap/approach any point where there is
a wall. Checking for walls like this should be easy, just check if we are approching a place where scene geometry goes up
in the Z-axis at an angle greater than 45deg. If the angle <= 45deg, then the entity should climb the incline, moving normally,
but also having its Z-coordinate incremented as it moves up the incline. The camera will follow entites along any axis, so it
will go up in Z automatically as the player climbs

I can use Diligent::GLTF::Mesh's .BB (bound box) property to get the bounding box of the mesh an entity is approaching,
this box is already in the standard format for AABB collision detection, only with 3D vec3 coordinates instead of 2D vec2

Now I need to determine where I am going to add the implementation for the collision detection.
This algorithm deals with collisions between entities as well as collisions betweens entities and 3D elements of the scene.
Because this mostly deals with the Entity, I want to put this handling as part of the Entity::update() function. The only
complication is the need to handle the 3D meshes' bounding boxes, which need to be obtained off the renderer via m_sceneMeshes,
A getter func cannot be used, Entity does not know about the renderer's existance. Possibly another callback can be used, but if I do that
I need to figure out what data I send, I don't want to make unecessary copies. I could pass a shared pointer to scene meshes, but that contains
other data like primitive data containing index counts and texture IDs which entity should have no access to. Again, entity should have no access

Expanding scene renderer for multiple textures
-=-=-=-=-=-=-=-=-=-=-=-=-=-=-=-=-=-=-=-=-=-=-=-=-

This isn't that difficult, since I am only using base colour. Other material components are unused, as they exist to provide
realism and visual depth that is not required for the style of this game. g_pSceneTextures need to be made into a proper texture array
sized according to the number of textures the glTF loader has detected in the scene
Looking at the back-end implementation of GetTexture() in the glTF asset loader, Diligent is internally loading all textures into a dynamic texture
atlas. That means most of the complex work is done already

A texture refers to just the raw image data of a loaded PNG (although diligent probably adds some metadata)
A material can take multiple textures as inputs and dictates the final appearence of the surface it is applied to based on the input textures

In terms of Blender, the materials use a principled BSDF node with only a base colour texture attached, the other parameters such as
the normal map or the 'metallic' and 'roughness' sliders are unused, everything that is not the base colour is left untouched.
The material output node has the principled BSDF linked to the surface shading slot. The other three slots are irrelevant and unused

In diligent's API, when accessing an individual primitive, a property of the Diligent::GLTF::Primitive struct is 'MaterialID' (uint32_t)
When loading any glTF, Diligent will have also auto-created the materials and placed them in the m_pGlbModel->Materials vector

So, to draw I want to assign textures per-primitive as each primitive has its own material. But I can't see how to access the textures
which a material takes as its inputs?

To investigate, I looked at the GLTFLoader header (DiligentTools/AssetLoader/interface/GLTFLoader.hpp) to see the declaration
of the Material struct and found these member function that dealt with textures:

Uint32 GetMaxActiveTextureAttribIdx() const
Uint32 GetNumActiveTextureAttribs() const

bool IsTextureAttribActive(Uint32 Idx) const

int GetTextureId(Uint32 Idx) const
void SetTextureId(Uint32 Idx, int TextureId)

TextureShaderAttribs& GetTextureAttrib(Uint32 Idx)
const TextureShaderAttribs& GetTextureAttrib(Uint32 Idx) const

GetTextureId() is the most useful one of these, as it returns the index of the texture you request
in the model's texture array. materials store texture IDs. A material can have up to 15 textures representing all the different possible input textures.
These texture attribs are stored in the material with indices 0 - 15. The one I care about is index 0, which
is 'DefaultBaseColorTextureAttribId', so I can call m_pGlbModel->Materials[primitive.MaterialId].GetTextureId(DefaultBaseColorTextureAttribId);
to get the texture associated with a single primitive

in renderScene() I already iterate over each mesh and primitive to get the primitive's attributes to issue the draw command.
Getting the correct texture for a primitive now depends on this iteration, but textures cannot be assigned to the SRV or SRB in an active render
pass (or at least that wouldn't be the ideal way to do it). I do not want to iterate twice over the same arrays. That is inefficient and lazy.
Instead, the iteration should be moved outside of the render and I can instead cache all the draw attributes for every primitive as well as the materials
assigned to them in a structure. This approach will also be helpful for the collision detection, since I'll also need to get the meshes' bounding boxes
anyway.

From Diligent Samples, tutorial 3:

Mutable resources are set through the object called shader resource binding, or SRB. SRB encompasses all resources specific to an object instance.
As an example, if your character shader uses a shadow map, diffuse and normal maps,
then shadow map should typically be static resource as it is the same for all object instances,
while normal and diffuse maps should be mutable as they are character-specific.
Shader variable type is defined by ShaderResourceVariableDesc structure. Recall that if shader variable type is not specified,
default type defined by DefaultVariableType is used.

A mutable resource can only be bound once to an SRB object. If multiple variations are required, a number of SRB objects should be created.
For a very frequently changning resources, dynamic variables can be used. Dynamic resources can be bound multiple times to the same SRB object,
but are less efficient from performance point of view. Refer to [this post] for more details.
Do not confuse shader variable type with resource usage. Shader variable type is all about binding resources to shader variables.
It has nothing to do with the ability to change the resource contents which is controlled by the resource usage.
